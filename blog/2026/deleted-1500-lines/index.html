I deleted 1500 lines and nothing broke

Created in February 03, 2026

2026   ·   python   engineering   refactoring   ai   ·   engineering

I had a codebase around 2000 lines doing something specific: coordinate a multi-step process, collect outputs, pass context between steps. The problem it was solving wasn’t complicated. The code was.

I kept adding to it — more error handling, better parsing, edge case coverage. The things that kept breaking were the same thing in different forms. I was treating an interface as something it wasn’t, and writing code to paper over the gap.

the subprocess problem

The system called an external tool via subprocess. The tool ran, produced text output, the system parsed that text to figure out what happened. This seems fine until it isn’t. Output formats drift. Error messages are written for humans, not parsers. Knowing whether something succeeded means interpreting text, which means your parser breaks whenever the wording changes. And any state the subprocess was tracking lives in its context, not yours — so if something fails mid-run, you’re reconstructing from logs.

Most of those 2000 lines weren’t solving the actual problem. They were a translation layer between two things that weren’t designed to talk to each other. Parser code. Retry code built around parsing failures. Workarounds for ambiguous output. The complexity wasn’t from the domain — it was from the interface mismatch.

the migration

When the tool released an SDK, migrating was mostly just deleting things.

Every subprocess.run became a direct SDK call. Every output parser became a typed response object. Every “what does this output mean” workaround became unnecessary because the SDK returned structured data. The context I’d been tracking manually across subprocess calls was handled by the SDK’s session model.

End result: around 500 lines. The behavior was the same. Things that had been flaky stopped being flaky, because they were no longer depending on text parsing staying consistent.

the thing I took from it

There’s a kind of complexity that comes purely from using a tool wrong — or using it in a way it wasn’t built for, which ends up the same thing. The adapter code accumulates. It has its own bugs. It needs its own tests. It becomes load-bearing infrastructure for problems that shouldn’t exist.

When you find yourself spending significant energy on parsing or workarounds or “making this work,” that’s usually the interface fighting back. Sometimes you don’t have a better option and you write the adapter and move on. But it’s worth noticing when you’re in that situation, because it tends to compound.

The 1500 lines I deleted weren’t badly written. They were the right code for the interface I had at the time. The new interface made them unnecessary, and the correct response to that is to delete them, not preserve them out of some attachment to the work they represented.
